# Loadouts — work in progress

**Status: EARLY. Category injection built, icon BROKEN, no loadout functionality yet.**

This folder holds unfinished work toward a named-loadout system. The finished, working feature in this
repo is the **sub-filters**; everything here is incomplete.

Full design brief lives in the modlist repo at
`Still in Skyrim Plus Documentation/SKYUI_LOADOUTS_BRIEF.md`.

## What works

**The LOADOUTS category is injected and appears in the inventory.** Added inside
`InventoryLists.SetCategoriesList()` so it survives the game re-sending the category list:

    this.categoryList.entryList.push({text:"LOADOUTS",flag:65536,bDontHide:true,savedItemIndex:0,filterFlag:1});

- `flag 65536` cannot collide with `Inventory.FILTERFLAG_*`, which occupy 1..1023, so no real item
  matches and the list stays empty
- `bDontHide:true` keeps the icon lit despite the category being empty
- `InventoryMenu._categoryListIconArt` has `"inv_loadouts"` appended as the 12th entry

## What is BROKEN — the icon

**The custom icon does not display. The frame shows `mag_activeeffects` art instead.**
Confirmed in game twice, including after an attempted fix. Do not assume it is fixed.

### What is known to be correct

- The source SVG is good: 128x128 viewBox, one path, `#FFFFFF`, no strokes, no gradients. It imports
  cleanly with no warnings.
- `ffdec-cli -replace <swf> <swf> 42 icon.svg` works and grows the file from ~8020 to ~8943 bytes, so
  the artwork **is** being written into shape 42.
- The frame label `inv_loadouts` exists and `inventorymenu.swf` references it.

### What was tried and did NOT fix it

A new frame was created by cloning the last icon group (`mag_activeeffects`). Each icon frame is five
tags:

    FrameLabelTag   name="inv_loadouts"
    DefineShapeTag  shapeId=42      <- our artwork lands here
    DefineSpriteTag spriteId=43
    PlaceObject2Tag characterId=42  <- places the shape inside the sprite
    ShowFrameTag
    PlaceObject2Tag characterId=43  <- places the sprite on the timeline
    ShowFrameTag

The clone originally left that **final** `PlaceObject2Tag` pointing at `41`, the donor's sprite. That
was corrected to `43` and verified in the XML, **and the icon still renders as active effects.**

So the mis-wired PlaceObject was a real bug but **not the only one**.

### Leads for whoever picks this up

1. **Check the shape actually renders.** Open the built
   `interface/skyui/icons_category_psychosteve.swf` in the JPEXS GUI (`tools/FFDec/ffdec.exe`) and look
   at shape 42 directly. If it is blank or malformed, the SVG import is subtly wrong (fill rule, winding
   order, or coordinate scale) even though it reported success.
2. **Check the shape bounds.** Existing icons declare `shapeBounds` around 2500 twips. If the imported
   SVG landed at a different scale or origin, it could be drawing off-screen. Compare shape 42's
   `shapeBounds` against a working icon's.
3. **Check frame ordering.** `gotoAndStop("inv_loadouts")` resolves by label, but the donor frame's
   `PlaceObject`/`RemoveObject` pairing may leave the previous frame's sprite on screen. Note there is a
   `RemoveObject2Tag` before `mag_activeeffects` that the clone did not reproduce.
4. **Consider a cleaner approach entirely:** give the entry its own icon source rather than adding a
   frame. `CategoryListEntry.initialize` reads `a_state.iconSource`, which is per-list. Adding a
   parallel `iconSourceArt` array on `CategoryList`, mirroring the existing `iconArt`, would let the
   LOADOUTS entry load a small standalone SWF. That avoids frame surgery altogether and survives icon
   packs.

### Known trap

**The SVG injection is a POST-BUILD step and is not in cmake.** A clean rebuild silently reverts the
icon to placeholder art:

    cmake --build build/debug --target ActionScript
    ffdec-cli -replace build/debug/interface/skyui/icons_category_psychosteve.swf \
                       build/debug/interface/skyui/icons_category_psychosteve.swf 42 skyrim_loadouts.svg

A `-swf2xml` round-trip back into the source XML was attempted so the build would reproduce it
automatically. **The frame label survived but the shape geometry did not**, so this does not work.
